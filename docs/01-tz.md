| Пункт | Значение |

## 1.2 Назначение и цели создания
**Назначение:** онлайн-маркетплейс (каталог товаров продавцов, корзина, оформление и оплата заказов, уведомления, аналитика продаж), который в обычном режиме работает при умеренной нагрузке, а в период распродаж (Чёрная пятница, флеш-акции со стартом в 00:00) выдерживает рост трафика в 10–50 раз.

**Цели:**
1. Выдерживать пик трафика на старте распродажи без отказа системы и без деградации ниже SLO.
2. Не допустить продажи товара сверх остатка (overselling) при тысячах одновременных покупок одного SKU.
3. Отсечь ботов и перекупщиков (rate limiting, лимит единиц товара на покупателя).
4. Обеспечить слабую связанность сервисов через событийную шину (EDA, Apache Kafka) — всплеск заказов буферизуется в Kafka и обрабатывается асинхронно.
5. Дать продавцам и бизнесу аналитику продаж в почти реальном времени.
6. Отработать полный цикл платформенной инженерии: IaC, GitOps, Service Mesh, Observability, CI/CD, нагрузочное тестирование.

## 1.3 Характеристика объекта автоматизации
Пользователи: покупатели (анонимные и зарегистрированные), продавцы, администраторы/SRE. Внешние системы: платёжный провайдер (в учебной версии — эмулятор), SMTP/Push-провайдер, Identity Provider (Keycloak).

Профиль нагрузки:
| Режим | Чтение каталога | Оформление заказов |
|---|---|---|
| Обычный день | ~500 RPS | ~20 заказов/с |
| Чёрная пятница, первые 15 мин после 00:00 | до 20 000 RPS | до 1 500 заказов/с |

## 1.4 Требования к системе
### 1.4.1 Требования к структуре
Аутентификация вынесена в готовый IdP (Keycloak, OIDC/JWT) — писать собственный user-service нецелесообразно. Доменные микросервисы (6 шт.), развёрнутые в Kubernetes:

| # | Сервис | Ответственность | Хранилище |
|---|---|---|---|
| 1 | `catalog-service` | товары, категории, акции, цены со скидкой, поиск | MongoDB + Valkey (кэш) |
| 2 | `inventory-service` | остатки по SKU, атомарное резервирование, возврат резерва | PostgreSQL + Valkey (горячие счётчики) |
| 3 | `order-service` | корзина, оформление заказа, оркестрация саги | PostgreSQL + Valkey (корзины) |
| 4 | `payment-service` | платежи, идемпотентность, вебхуки провайдера | PostgreSQL |
| 5 | `notification-service` | e-mail/push о статусе заказа, ретраи, DLQ | MongoDB |
| 6 | `analytics-service` | продажи в реальном времени, холодное хранилище событий | ClickHouse + S3 (MinIO) |

Слой роутинга: Keepalived (VIP) → HAProxy ×2 → Envoy Gateway (Gateway API, JWT, rate limiting с бэкендом Valkey, виртуальная очередь ожидания) → Istio mesh → сервисы.

### 1.4.2 Требования к функциям (кратко; подробно — в User Stories/Use Cases)
- F1. Вход через Keycloak (OIDC), получение JWT.
- F2. Просмотр и поиск товаров, просмотр акций Чёрной пятницы с обратным отсчётом.
- F3. Корзина (хранится в Valkey, TTL 7 дней).
- F4. Оформление заказа с резервированием остатков на 15 минут, без overselling.
- F5. Оплата заказа, идемпотентная обработка повторов.
- F6. Уведомления о статусе заказа.
- F7. Отмена/истечение резерва с возвратом остатков.
- F8. Аналитика продаж для продавца и бизнеса (задержка ≤ 1 мин).
- F9. Виртуальная очередь ожидания (waiting room) при перегрузке.
- F10. Лимит акционного товара на покупателя (например, не более 2 шт.).

### 1.4.3 Требования к надёжности
- Доступность публичного API ≥ 99.9 % в период распродажи, ≥ 99.5 % в месяц.
- Отказ одного экземпляра любого сервиса или одного узла HAProxy не приводит к недоступности системы.
- Отказ payment-провайдера не роняет каталог и корзину (изоляция через Circuit Breaker).
- Kafka: replication factor 3, `min.insync.replicas=2`, `acks=all`.
- RPO ≤ 5 мин для PostgreSQL (WAL-архив), RTO ≤ 30 мин.

### 1.4.4 Требования к производительности
- Каталог: 20 000 RPS в пике, p95 ≤ 150 мс (≥ 95 % запросов обслуживаются из кэша).
- Оформление заказа: 1 500 заказов/с в пике, p95 ≤ 400 мс.
- End-to-end «оплата → уведомление» ≤ 10 с (p95).
- Время масштабирования: новые поды готовы ≤ 60 с; плановый прогрев (pre-scaling) за 15 мин до старта акции.

### 1.4.5 Требования к безопасности
- TLS на входе, mTLS внутри mesh (Istio STRICT).
- JWT (RS256, Keycloak), валидация на шлюзе.
- Секреты — Kubernetes Secrets, создаваемые Terraform (в перспективе External Secrets / Vault).
- Сетевые политики Cilium: default-deny, разрешения по сервисам.
- Антибот: rate limiting по IP и по пользователю, лимит единиц акционного товара на покупателя.

### 1.4.6 Требования к эксплуатации и наблюдаемости
Метрики, логи, трейсы через OpenTelemetry; дашборд «Black Friday war room» в Grafana; алертинг по SLO (см. `06-observability.md`).

### 1.4.7 Требования к видам обеспечения
- Программное: Kubernetes (k3s / Talos), Cilium, Istio, Envoy Gateway, Strimzi Kafka, PostgreSQL (CloudNativePG), MongoDB, ClickHouse, Valkey, MinIO, Keycloak, ArgoCD, Terraform, Ansible, Helm, GitLab CI + Kaniko, KEDA.
- Языки сервисов: Python (FastAPI) / Go (inventory и order — Go, как самые нагруженные).
