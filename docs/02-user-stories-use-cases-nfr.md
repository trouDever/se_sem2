# 2. User Stories, Use Cases, NFR

## 2.1 User Stories
| ID | Роль | История | Критерии приёмки |
|---|---|---|---|
| US-01 | Покупатель | Как покупатель, я хочу войти через единый аккаунт, чтобы видеть свои заказы | Вход через Keycloak (OIDC), JWT действует 15 мин, refresh-токен |
| US-02 | Покупатель | Я хочу искать товары по категории, цене и скидке | Ответ ≤ 150 мс (p95) даже в пик распродажи |
| US-03 | Покупатель | Я хочу видеть акции Чёрной пятницы с таймером до старта | Цены со скидкой становятся доступны ровно в момент старта |
| US-04 | Покупатель | Я хочу добавлять товары в корзину | Корзина сохраняется 7 дней, доступна с разных устройств |
| US-05 | Покупатель | Я хочу оформить заказ и быть уверенным, что товар действительно есть | Товар резервируется на 15 мин; продать больше остатка невозможно |
| US-06 | Покупатель | Я хочу оплатить заказ картой | Повторный клик «Оплатить» не списывает деньги дважды |
| US-07 | Покупатель | Если сайт перегружен, я хочу видеть своё место в очереди, а не ошибку | Waiting room с номером в очереди и ожидаемым временем |
| US-08 | Покупатель | Я хочу получать уведомления о статусе заказа | Письмо ≤ 10 с после оплаты (p95) |
| US-09 | Продавец | Я хочу загрузить товары и остатки и задать акционную цену на Чёрную пятницу | Акция активируется автоматически в заданное время |
| US-10 | Продавец | Я хочу видеть продажи в реальном времени во время распродажи | Задержка аналитики ≤ 1 мин |
| US-11 | Администратор/SRE | Я хочу видеть состояние системы и получать алерты | Дашборд «war room» в Grafana, алерты в Telegram |
| US-12 | Платформа | Я хочу ограничивать ботов и перекупщиков | 429 при превышении лимита; не более N единиц акционного товара на покупателя |

## 2.2 Use Cases

### UC-1. Оформление заказа в пик распродажи
- **Актор:** покупатель (аутентифицирован). **Предусловие:** в корзине есть товары, акция активна.
- **Основной сценарий:**
  1. Покупатель нажимает «Оформить заказ».
  2. Gateway проверяет JWT, глобальный rate limit и состояние waiting room.
  3. `order-service` создаёт заказ `NEW` и синхронно вызывает `inventory-service` `POST /reservations`.
  4. `inventory-service` атомарно (Lua-скрипт в Valkey) проверяет лимит на покупателя и уменьшает счётчики `stock:{sku}` для всех позиций (всё-или-ничего), сохраняет резерв в PostgreSQL с TTL 15 мин и публикует `inventory.reserved`.
  5. `order-service` переводит заказ в `RESERVED`, публикует `order.created` (outbox → Kafka) и возвращает клиенту `order_id` и ссылку на оплату.
- **Альтернативы:** 4a. Товар закончился → 409 «Нет в наличии», частичные списания откатываются. 4b. Превышен лимит на покупателя → 422. 2a. Лимит запросов превышен → 429. 2b. Система перегружена → клиент попадает в waiting room.

### UC-2. Оплата и подтверждение
1. Покупатель отправляет `POST /payments` с `Idempotency-Key`.
2. `payment-service` вызывает провайдера, сохраняет платёж, публикует `payment.succeeded`.
3. `order-service` потребляет событие, переводит заказ в `PAID`, публикует `order.paid`.
4. `inventory-service` фиксирует резерв (`committed`), `notification-service` отправляет письмо, `analytics-service` пишет событие в ClickHouse.
- **Альтернатива:** `payment.failed` → заказ `CANCELLED`, публикуется `order.cancelled`, `inventory-service` возвращает остаток (компенсация саги).

### UC-3. Истечение резерва
Неоплаченный резерв истекает через 15 мин: планировщик в `inventory-service` (раз в 30 с) возвращает остатки (`INCRBY stock:{sku}`), публикует `inventory.released`; `order-service` переводит заказ в `EXPIRED`.

### UC-4. Запуск акции Чёрной пятницы (продавец)
Продавец задаёт акционную цену, остаток и время старта → `catalog-service` публикует `catalog.promo-scheduled` → за 15 мин до старта: прогрев кэша каталога, `inventory-service` загружает остатки в Valkey, KEDA cron-триггер заранее увеличивает число подов.

### UC-5. Вход в waiting room
При превышении порога активных сессий gateway выдаёт покупателю токен очереди (номер в упорядоченном множестве Valkey); каждые N секунд пропускается следующая партия; клиент опрашивает `/queue/status`.

### UC-6. Просмотр аналитики
Продавец открывает дашборд продаж → `analytics-service` выполняет агрегирующий запрос к ClickHouse (материализованные представления: продажи по минутам, топ-SKU, конверсия корзина → оплата).

## 2.3 Нефункциональные требования (NFR)
| ID | Категория | Требование | Как проверяем |
|---|---|---|---|
| NFR-01 | Производительность | 20 000 RPS каталога (p95 ≤ 150 мс), 1 500 заказов/с (p95 ≤ 400 мс) | Locust, сценарий «00:00» + Grafana |
| NFR-02 | Эластичность | Рост трафика в 10–50 раз за минуты: HPA + KEDA (cron + Kafka lag) + автоскейл нод | нагрузочный тест со ступенчатым ростом |
| NFR-03 | Доступность | ≥ 99.9 % во время распродажи; нет SPOF на входе (Keepalived VIP, 2× HAProxy) | отключение узла HAProxy под нагрузкой |
| NFR-04 | Согласованность | Нет overselling: продано ≤ исходного остатка для каждого SKU | сверка после конкурентного теста на 1 SKU |
| NFR-05 | Надёжность доставки | at-least-once + идемпотентные консьюмеры; transactional outbox | рестарт консьюмеров под нагрузкой |
| NFR-06 | Отказоустойчивость | Circuit Breaker / outlier detection, retries с бюджетом; отказ оплаты не влияет на каталог | fault injection Istio (задание 6.2) |
| NFR-07 | Деградация | При перегрузке — waiting room и отключение второстепенного (рекомендации), а не 5xx | нагрузка выше расчётной |
| NFR-08 | Безопасность | TLS, mTLS, JWT, NetworkPolicy, rate limiting, лимит на покупателя | проверка конфигов, 429/403/422 |
| NFR-09 | Наблюдаемость | 100 % сервисов экспортируют OTel-метрики/логи/трейсы; сквозной trace-id | Grafana Explore |
| NFR-10 | Хранение | Горячие события 7 дней в Kafka, холодные — ClickHouse/S3 ≥ 1 года | политики retention |
| NFR-11 | Сопровождаемость | Вся инфраструктура описана кодом (Terraform/Helm/Ansible), деплой через GitOps; freeze изменений за 48 ч до распродажи | ArgoCD sync status |
